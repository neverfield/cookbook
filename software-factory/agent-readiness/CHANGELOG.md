# Changelog

## 0.2.0 (unreleased)

The release tag is `agent-readiness-v0.2.0`, the one `skill/agent-readiness/RELEASE.json` names and the README Quickstart clones. It doesn't exist yet: it is created when this release passes its gate (`support/RELEASE.md`: the Mac release run, a passing blind holdout test and an empty `tests/known-failures.json`). Until then, a report that says "Scripts match the agent-readiness-v0.2.0 manifest" describes a release candidate.

New audits use rubric `2026-12-beta`. Audits sealed under earlier rubrics are never rescored, and their reports render as before. Its text changed during 0.2, so its digest moved: an eval or release run bound to an earlier `2026-12-beta` digest needs a rerun.

### What a 0.1 user will notice first

- **Narration is a choice, not text.** `readiness narrate` takes ids: `--lead <component>`, `--cause <condition>=<evidence>`, `--works <ev,ev>` and `--ask <item>|settle`, or `--file` with the same keys. The report writes the headline, the ask and the gaps from the audit's own records. `--headline`, `--gap` and `--title` exit 2, as does an id that isn't a choice, with the list of choices. `readiness status` lists every choice with what part 1 would say for it. Free text belongs in the agent's reply. Narration files written for 0.1 no longer work.
- **"Undetermined" beside "unproven".** A level is undetermined when no Level 1 check failed but one couldn't be decided: a test runner the audit's own install left out, a system library missing from an image the audit picked, tests found but no command that runs them. The heading starts "Undetermined:", no level is named, confidence is low, and the report says what settles it (add a command, declare an environment, or rerun). Level 0 now needs a failure the audit attributes to the repo.
- **Sessions.** `readiness session start` opens an audit's session, `init` joins it, and the seal, `readiness session end` or 4 hours without a write releases it. The user's yes to host mode is held by the session and cleared at the seal; `host-yes.json` is gone.
- **The shell guard is opt-in.** The SKILL.md preflight no longer installs it. `readiness guard install` is the user's choice, `readiness guard uninstall` puts `.cursor/hooks.json` and `info/exclude` back byte for byte, and `readiness guard status` says whether it is installed and enforcing. It works in a git worktree, and it enforces only inside a session; outside one the repo's commands run, but it still refuses reads of the draft records and the fault store.
- **A disposable cloud VM can prove Level 1.** A Cursor Cloud Agent VM is detected, never declared. Consent is unchanged: the agent still asks before repo code runs on the host. On a detected VM the tests run with the network cut where the VM allows it; where it can't, the report says "with the network on" and caps confidence at medium. `SA_READINESS_VM_DETECT=off` turns detection off. The wording reads "in a clean environment", and "a clean container or a disposable VM".
- **Docker only.** `auto` tries Docker, and `--runtime podman` is refused until rootless Podman is tested. Change any CI or script that passes it to `docker` or `auto`.
- **Nothing left behind.** Containers start with `--rm`, live at most the budget plus two hours, and carry owner and host labels. SIGINT, SIGTERM, SIGHUP and exit tear down containers, host process groups and temp folders. `init`, `replay` and `recheck` reap leftovers whose owner is gone. `readiness cleanup` removes this repo's stray drafts and unlabeled temp folders and `readiness-aud-*` containers older than 4 hours; `--images` also removes the `readiness-env-*` images.

### Results

- **Every change is counted.** Discovery places every folder that holds a manifest exactly once: component, member, satellite, excluded or unplaced. Each counted change goes to the deepest component, else the satellite that lists it, else nobody, and the unowned share (`components.unownedShare`) counts toward partial coverage. A workspace root that runs tests itself is a component; members CI tests from the root roll into it; every Go module with Go source is its own; a folder-name hint (plugins/, docs/) demotes only while it holds under half the changes. Make test targets, tox and the pytest extras in `[project.optional-dependencies]` are found.
- **The command CI runs.** For a Node component, the test script CI runs in its folder (`.github/workflows/*.yml` `run:` steps) outranks the manifest's `test` script, narrowed to the one script that runs a test runner, with the step's literal variables. Each command records its tier and confidence. An exact `engines.pnpm` or `engines.yarn` pin sets corepack's default.
- **Experiments before blame.** A test run that fails with the network cut runs once more with it on; a pass proves Level 1 "with the network on", at medium confidence. When that rerun fails too, it gets one more try with the network on: a pass there records the tests as flaky, naming what the failed try failed on, instead of Level 0; a third failure is the repo's. A test run blocked by a missing git, in an image the audit picked, runs again once the audit adds git.
- **Level 2 faults are an estimate.** Faults are planted in batches of 5, up to 20 with a clear result (30 at most). Strong needs the 97.5% Wilson lower bound at 40% or more and a 60% catch rate; weak is a 95% upper bound below 70%; anything else is inconclusive and undetermined, never a fail. A fault's id hashes its file, line and operator, so editing a test never redraws the set, and a re-audit replants the last sealed faults first. A fault run gets 10 times the clean run, 30 to 300 seconds. Direct pytest and `node --test` runs are narrowed to the tests that import the fault's file.
- **A type-check must be seen to fail.** When a component's type-check passes, the audit adds one known type error to the most recently changed TypeScript or Python file the component's tests import, in its throwaway copy. The type-check must fail on it and pass again once it is removed before the commands condition counts at Level 2. A type-check that passes with the error in place doesn't check that file, so the component stays at Level 1, and a new roadmap step, "Make `<component>`'s type-check cover `<file>`", names the file and the line. Components whose tests import no TypeScript or Python file are exempt and count on the exit code alone, and the report says so. See [checks.md](skill/agent-readiness/references/checks.md#verifycanonical_interface-build-lint-type-check-and-test-commands-pass).
- **Secrets by class.** Provider tokens, private keys and credentials in URLs block Level 2 in shipped code. A generic `API_KEY = '...'` is listed for review with its name and length, never its value, and template URLs are placeholders. Advice says "rotate" only for a blocking class and never tells a tracked source file to go in `.gitignore`.
- **Instruction severities.** A wrong command in a file written for agents (AGENTS.md, CLAUDE.md, Cursor rules and skills, Copilot instructions) holds Level 2. Wrong README and CONTRIBUTING items, and wrong paths anywhere, are listed for the reader and don't gate.
- **Resource limits are never the repo's failure.** An out-of-memory kill or a full disk is a `resource` diagnosis with a `limit` (memory or disk), blocked on this machine with how to raise it. `replay`, `recheck` and `audit` take `--memory <MB>` (`SA_READINESS_MEMORY_MB`).
- **A test's own git identity wins.** The audit's fallback identity is a git config file at system scope (`GIT_CONFIG_SYSTEM`), git's lowest, instead of `GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables, which overrode the identity a test sets in its own temporary repo. A test that commits without setting one still gets "Agent Readiness <readiness@audit.invalid>". Host mode's system git config is replaced by that file, as its home already is.
- **The uv image is on Debian trixie.** Python projects managed with uv replay in `ghcr.io/astral-sh/uv:python3.x-trixie-slim`, the same Debian release as the `python:3.x-slim` images, instead of bookworm-slim. When a test needs git, the audit adds trixie's git 2.47 rather than bookworm's 2.39, which failed tests that pass on current CI runners.
- **A planted fault can't outlive its run.** Each planted fault, and the original put back after it, is written with a whole-second modification time later than any before it. A narrowed test run often finishes in under a second, and Python reused the cached bytecode of a same-size fault after the original was back, so one fault failed later unrelated runs and counted them as caught; cleo read Level 2 or Level 1 from run to run. It now reads Level 1 every time.

### The report

- **One model.** Every fact is derived once (`lib/model.ts`), and the Markdown and HTML views only lay it out. The repo level and every component carry `status` (proven, unproven, undetermined, not_assessed), `provenIn` and `settleBy`. An unproven result names no level: "Unproven on this machine (could be 1)". Skipped items have their own count.
- **Current evidence.** A rerun of the same check replaces the old row in scoring; the evidence log keeps the old row folded under its replacement. Every row has a duration and a pasteable `repro`.
- **What the audit assumed.** Page 1 has a folded block with the component map, each command and the file it came from, where commands ran and the toolchain versions. The record states whether the seal is unsigned or keyed.
- **Visible runs.** A running command prints a line at least every 30 seconds, each result line has its duration, and the replay ends with time by component and the `--budget-component` or `--budget-total` value to rerun with.
- **Environment self-check.** Before any repo command, a canary checks that the work tree is present and writable, the uid and git identity, and for a container that the network goes down. A failure blocks every check with "the audit's environment failed its self-check", never a repo failure. The audit sets git's identity and `TZ=UTC`.
- **Masked values.** A secret-shaped string in the repo's own text is masked at the seal as `[redacted:<type>]`, and "About this report" says how many and where; a registry value never reaches the report through failure text. A value passed with `--registry-env` still refuses. The audit schema gains an optional `masked` list.
- **Revert rate in the outcomes (reported only).** Part 3's outcome table has a "Reverted within 14 days" row for agent and other PRs. `readiness outcomes` finds reverts from merged revert PRs ("Reverts #123" in the body, or a `Revert "<title>"` title) and from "This reverts commit" lines on the default branch, and the report names each reverted agent PR. No level, target or Level 4 rule reads it yet. Recorded PR files can carry `revertedAt` and `revertedBy`; without them the row reads "not measured".
- **A scripted way to drive the app (informational).** A new signal in part 5 looks for Playwright, Cypress or WebdriverIO specs, a `verify-<app>` skill with a Drive section or a feature map, a smoke script or a terminal harness, for each component that is an app. It is never scored. When a component at Level 2 is an app with none of these, the roadmap adds a later step, "Give agents a way to drive `<component>`", after "Give agents work in" it. The agent assets list marks `verify-<app>` skills and the size of their feature maps.
- **Templates say what the agent used to add.** The headline names components found but not assessed, or outside a sampled audit, when it fits the 40-word limit; the Level 1 template has a shortest variant without the change share; `--ask settle` renders what settles an unproven or undetermined level.

### Machines, consent and edge cases

- **The guard holds only during a session.** Outside one it refuses nothing, so a repo's own `db/seed.txt` or `mutants.json` stays readable; in one, a read is held only when it points into the audit's own folders. Uninstall restores `.cursor/hooks.json` byte for byte when nothing else in it changed, and `guard status` runs the hook to show it answers.
- **The user's yes is on the record.** "About this report" quotes the yes recorded with `readiness allow-host --note`, or says host mode ran on the flag alone.
- **A maintainer can correct a command.** `.agent-readiness/config.json`, committed, names the install, build, lint, type-check or test command for a component, with a reason and a reviewer; it replaces the scan's commands of that kind there.
- **Rerun commands that work.** Part 5's rerun commands use the pinned image, run as your user with the audit's home and `CI=1`, keep the image's PATH, and say the network stays on and to use a fresh clone.
- **Any skills folder.** The skill excludes itself under `.claude/skills/`, `.agents/skills/` or wherever it is installed, not only `.cursor/skills/`.
- **Clear machine limits.** A full temp disk stops before the copy with what it needs (`TMPDIR` moves it); a container that can't see the temp folder gets a second try under `~/.cache/agent-readiness/`; a first image pull has its own 30-minute limit (`SA_READINESS_PULL_MINUTES`); a planted-fault run stopped at the memory limit counts neither way; change shares that can't be read say so.
- **Private packages.** A "not found" for a scoped npm package or from an internal Maven, NuGet, pip or Go registry reads as a private package that needs its credential.
- **A broken declared image is a finding.** A `.cursor/Dockerfile` that doesn't build fails the install and the audit seals; a base image that can't be pulled blocks it.
- **Placeholders and test keys aren't leaks.** A password in a URL that names itself, as in a commented chart example's `proxy_user:proxy_password@`, is a placeholder. A file that imports a test framework (vitest, Jest, `node:test`, Mocha, Playwright, pytest or unittest) is a test whatever its name, so a key in a `*.servertest.ts` file is listed for review. A real password in a comment and a key in shipped code still block.
- **The solution decides what a .NET folder builds.** With a solution there, only the projects it lists are restored, built and tested, so a stale benchmark or Arcade's vendored `eng/common` tooling outside it no longer reads as a repo that doesn't build. An SDK pin nothing here satisfies ("A compatible .NET SDK was not found", or NETSDK1045) is blocked on this machine, not a failure.
- **Host mode on an older Node.** Outside a container, a failed command is blocked on this machine when a locked dependency's `engines.node` needs a newer Node than the one here, and the report names the package. So is a corepack too old to start the package manager it fetched, as Node 22.14's corepack with pnpm 12.
- **Commands carry their folder.** The report writes a command run outside the repo root as "`corepack pnpm run test` in `dev-packages/browser-integration-tests` (blocked)", so components that run the same command line each read with their own result.
- **Hygiene.** `history push` runs none of the repo's hooks or signing; `cleanup` removes only folders an audit marked; host-mode background processes end with the replay; a printed private key is redacted whole; Microsoft's .NET install script is pinned and checked.

### Install and release

- The README Quickstart clones `--branch agent-readiness-v0.2.0`, and the example CI workflows name that release and ask you to pin the commit it points to. `npm run release-manifest` refuses to write `RELEASE.json` when the Quickstart or either workflow names another release.
- The holdout adapter's one-fact check (K6) reads a blocked command's word only in the explanations about its own component, keyed by contract and component, so in a monorepo another package that runs the same command line and fails on its own no longer reads as a conflict. An instrument change: `support/holdout/observe.ts` only; `score.ts` and the frozen protocol files are unchanged.
- Narration is outside the release gate: the headline judge lift is reported, not required (`RELEASE_POLICY.narrationLift` is false). A release needs a passing blind holdout test and an empty `tests/known-failures.json`.

Later work, not in this release: a planted lint error (lint configs differ too much between repos to plant one error every config flags, so "whether the lint command catches anything" is listed as not assessed), a revert-rate target, a review-capacity guard for Level 4, scoring the drive-the-app signal, a committed component-map override, and rootless Podman.
