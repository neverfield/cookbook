# The checks (rubric 2026-12-beta)

> Preview: agent-readiness 0.2 is pre-1.0; results and scoring may change.

Six checks, plus an informational inventory of agent assets. The checks are the same under 2026-10-alpha; 2026-11-alpha changed Levels 3 and 4, the repo rollup and the action matrix, which [levels.md](levels.md) describes, 2026-11-beta changed how planted faults are chosen and how many must be caught, and assesses up to 10 components instead of 6, and 2026-12-beta requires a passing type-check to fail on a planted type error, decides planted faults by a sequential estimate, blocks only on three classes of secret, and gates only on agent instruction commands. What the audit supports, stack by stack, is in [supported.md](supported.md). Each check lists what it runs, when it passes, the evidence strength it needs, why it matters, and the usual fixes.

Evidence strength, weakest to strongest: stated in docs (`asserted`), read from files (`static`), ran on host (`executed`), ran in a clean container (`clean_replay`), confirmed by outcomes (`outcome_validated`). A check passes only at its required strength. A pass below it reads "not proven", never "passed".

## `scope.profile`: components and where changes land

Informational. Walks the whole tree for manifests at any depth: workspace packages (npm, pnpm and yarn workspaces), standalone Node and Python packages, projects in the other toolchains it scores (`.sln` solutions and `.csproj`, `.fsproj` and `.vbproj` projects, `go.mod`, `Cargo.toml`, `pom.xml`, `build.gradle`, `build.gradle.kts`, `Gemfile` and `composer.json`), and projects in toolchains it recognizes without scoring (`Package.swift`, `pubspec.yaml`, `CMakeLists.txt` or `meson.build`, an Android Gradle build, and any folder of `.tf` files, root module included). Each becomes a component with its own scripts, lockfile and install. Next to a root package, a nested package counts only with its own lockfile. A solution groups the projects under it; a root with several solutions is named after the one that matches the repo, or after the repo. Unsupported components are listed as not assessed with the reason ("isn't supported yet", linking [supported.md](supported.md)) and keep their share of changes. Poetry, Bun, Yarn 2 or later and uv workspaces are installed with their own frozen install; each member of a uv workspace is a component, installed from the root `uv.lock`. Yarn 2 or later with no version pin is recognised and not assessed yet, rather than installed with the wrong Yarn.

An app next to a root `package.json` is its own component and takes the root's files of its type plus everything that isn't a Node file. A PHP, Ruby, Go, Rust or JVM app there is assessed in its own toolchain's image; a Python app there isn't assessed yet ([supported.md](supported.md) says why). When that app isn't assessed and the root package has no test script, the root package goes with it and isn't assessed on its own either; the report says so, so release tooling at the root never makes the repo "have no tests".

A nested manifest under a folder that usually holds tests, samples or tooling (`test`, `tests`, `spec`, `e2e`, `sample`, `example`, `demo`, `bench`, `plugin`, `util`, `config`), another toolchain's project under a packaging folder (`HomebrewFormula`, `pkg`, `packaging`) or under an `android` or `ios` folder of a React Native, Capacitor or Flutter project, or a shared config package such as `@acme/eslint-config`, is a satellite: it's listed in part 5, not made a component, and only becomes one when the repo has nothing else to assess.

Each component's share counts changed files over 90 days. Bot authors, lockfile-only commits, generated files and renames don't count. The most active ten supported components are assessed (six under rubrics before 2026-11-beta); when there are more, the report labels the scope "sampled" and lists the rest. Part 5 lists every component found, included or excluded, with its path, toolchain, manifest, lockfile and reason. Whenever a component that isn't assessed holds a share of changes, part 1 says how much, by name.

## `scope.agent_assets`: agent assets in the repo

Informational and never scored. Lists AGENTS.md and CLAUDE.md, skills (`.cursor/skills`, `.claude/skills`, `.agents/skills`), rules, hooks, environment config, MCP config and Copilot instructions, with git authors, the last change and whether their commands replay. Skill frontmatter must have a `name` and a `description`. A skill named `verify-<app>` is marked as a verify skill, with the number of features in its feature map (the Markdown files in its `features/` folder), or with no feature map. It shows who in the repo already builds agent setup; it is never a reason for a recommendation by itself.

## `bootstrap.cold_replay`: setup works from a clean checkout

- **Runs:** the frozen install (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install --frozen-lockfile`, `uv sync --frozen`, or a virtualenv install from requirements), then each component's build and full test suite, in a clean container started from the repo's pinned toolchain. The network is on for install and build, and off for tests. A repo-declared `.cursor/environment.json` install and start replace the defaults, and a declared `.cursor/Dockerfile` is built and used as the image.
- **Passes:** each step exits 0 in the container. A pass on the host or in a fresh copy on the host is "blocked on this machine", because it can't rule out a service or tool the machine already had.
- **Blocked, not failed:** with no container runtime, a step that fails because this machine lacks a tool (`dotnet: command not found`), a setup command that uses `sudo`, and every step behind a blocked install are blocked. In a container, a tool missing from an image the audit picked (not one the repo declared), a network, TLS, certificate or proxy error, or an HTTP error from a package mirror (apt's `403  Forbidden` from deb.debian.org, or a 403, 407, 429 or 5xx from npm, Yarn, pnpm or PyPI), during the doctor, install, build or start step, and a build or test that fails because a sibling workspace package wasn't built first are blocked too. So are, at any step, a home or cache directory the audit's user can't write (`EACCES`, a `PermissionError`, npm's root-owned cache), a Python older than the project's `requires-python`, and Playwright browsers that aren't installed, unless the repo's own image is the one missing them. Commands share `HOME=/tmp/home`, which belongs to the user they run as; the audit's own setup as the image's user writes its caches elsewhere. Where no `.python-version` pins one, the audit's Python image is new enough for `requires-python`. Blocked never counts against the repo and never counts as met. When the repo's declared image installs the missing tool, the report says so. The container gets the host's `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY`, and its CA settings (`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`) with the files they name mounted read-only.
- **Also records:** whether a frozen install left the lockfile unchanged, and whether the toolchain is pinned (`.nvmrc`, `engines.node`, `packageManager`, `.python-version`). Repo-wide changes need both.
- **Needs:** ran in a clean container.
- **Why:** every agent starts from a clean checkout, so setup that only works on a prepared machine breaks every agent run. In the BootstrapAgent study, a reusable, verified setup cut later agents' token use by 25.9% and build time by 22.3%, measured on the study's benchmark repositories ([arXiv 2605.15815](https://arxiv.org/abs/2605.15815), [code](https://github.com/Vossera/BootstrapAgent)).
- **Usual fixes:** a service the tests expect on localhost (start it in the setup's start script), a credential the tests read (fake it), a lockfile that isn't committed, a registry token (pass its name with `--registry-env`).

## `verify.canonical_interface`: build, lint, type-check and test commands pass

- **Runs:** every discovered or documented build, lint, type-check and test command at `HEAD`. Lint runs before the build, so it never reads build output; one that fails there runs again after a build that passed. Lint and type-check run check-only: write flags such as `--write`, `--fix` and `--unsafe` are removed, `prettier`, `ruff format`, `black` and `isort` run in their check mode, and the report shows the command that ran next to the one the repo declares. The supported tools are listed in [supported.md](supported.md).
- **Passes:** all of them exit 0, and a test command exists. Stale documented commands count as failed, not missing. A lint or type-check that still changes the repo's files fails, and the files are put back before faults are planted.
- **The type-check must be able to fail (from 2026-12-beta):** once a component's type-check passes, the audit adds one line with a known type error, `const __readinessTypeCanary: number = "agent-readiness";` for TypeScript or `__readiness_type_canary: int = "agent-readiness"` for Python, to the end of the most recently changed TypeScript or Python file the component's tests import, in the throwaway copy. The type-check must fail with the line there and pass again once it is removed. If it passes with the line there, it doesn't check that file, so the condition isn't met and the roadmap step says which file to cover. If it fails again without the line, the result is unproven, not failed. A component whose tests import no TypeScript or Python file is exempt and counts on the exit code alone, as are JavaScript (whose type-check often checks only `.d.ts` files) and the other languages, and the report says so. Every checker of the two languages reports the line at any strictness, so it can't fail a type-check that really covers the file. Lint has no planted error yet, so whether the lint command catches anything is listed as not assessed.
- **Needs:** ran on host or stronger.
- **Why:** agents need one known way to check their own work before they push, and a check that has never been seen to fail proves nothing. That rule comes from practitioners' verification tooling ([pstack](https://github.com/cursor/plugins/tree/main/pstack): "a check that you have never seen fail proves nothing"). Caveat: it is a working rule, not a measured result. A `typecheck` script that only loads the code (`node --experimental-strip-types`), a tsconfig that doesn't include the source, or a checker pointed at another folder all exit 0 and check nothing agents change.
- **Usual fixes:** fix the failing command on the main branch; add a missing test or lint script; point the type-check at the source the tests import.

## `verify.behavioral_oracle`: tests catch planted faults

- **Runs:** in a throwaway copy, the scripts plant faults (5 per component under 2026-11-beta, batches of 5 under 2026-12-beta) in files the component's tests cover (the files they import, or for Go, Rust, the JVM, .NET, PHP and Ruby, the source their language file names), most recently changed first. The operators flip a comparison boundary, negate a condition, shift by one, swap a boolean return, drop a throw or early return, or change a constant. Faults are chosen from the code, so the same code always gets the same faults and the result changes only when the code does; under 2026-11-beta the pick is keyed on the tests too, so changing them plants different faults. Under rubrics before 2026-11-beta the seed is fresh for each audit. TypeScript, JavaScript, Python, Go, Rust, Java, Kotlin, C#, PHP and Ruby are supported; a fault in a compiled language is discarded, never counted, when it doesn't compile.
- **Flake guard:** the suite must pass twice before any fault is planted. Under 2026-12-beta a caught fault runs once (`mutation.caughtRuns`), since those two clean runs already cover flakiness; under earlier rubrics it counts as caught only if the suite fails on two runs. A fault that breaks compilation is discarded, not counted.
- **From 2026-12-beta:** faults are planted in batches of 5 until the share caught is decided, up to 20 with a clear result (`mutation.estimate`). Each fault is ranked by its own file, line and operator (`mutation.identity`), so editing a test, or code in another file, never redraws it, and a re-audit plants the last sealed audit's faults again first, then fresh ones. Where the test command is a direct pytest or `node --test` run that names no paths, each fault runs only the tests that import its file, directly or through other files, once that narrowed run has passed on the clean tree; a file a `conftest.py` or test setup file reaches runs the whole suite (`mutation.scoped`).
- **Passes:** under 2026-12-beta, when the estimate is strong: the one-sided 97.5% Wilson lower bound on the share caught is at least 40% and the share at least 60%. It fails when the estimate is weak: the one-sided 95% upper bound is below 70%. Anything between is inconclusive, and the faults condition is undetermined, not failed. At 5 faults, 5 caught passes, 0 or 1 fails, and 2 to 4 plant another batch. A suite that catches 40% of faults passes under 5% of the time and one that catches 80% fails under 2% (`tests/level2-gates.test.ts`); on the calibration draws (`support/evals/calibration/fault-estimate.json`) 7 of 8 components get one verdict from every starting draw, against 2 of 8 under the 60% kill rate. Under 2026-11-beta the tests must catch at least 60% of the counted faults (`mutation.killRate`; earlier rubrics need every one), and at least 3 must give a clear result. Coverage alone never passes.
- **Needs:** ran on host or stronger. Level 2 also needs Level 1, which needs a clean container.
- **Why:** green tests aren't proof that a change is right.
  - OpenAI's SWE-Bench Pro audit flagged 200 of the 731 public tasks automatically (27.4%) and found 249 in human review (34.1%), so OpenAI estimates about 30% are broken, including low-coverage tests that let incomplete fixes pass. Caveat: an audit of one benchmark ([Jul 8, 2026](https://openai.com/index/separating-signal-from-noise-coding-evaluations)). It also sets a design rule here: a planted fault must be one any correct suite catches, not one tied to a particular implementation.
  - OpenAI's SWE-bench Verified audit found material test or description flaws in 59.4% of 138 tasks that o3 failed inconsistently. Caveat: that rate is within a selected subset of about 27.6% of the benchmark, not the whole benchmark.
- **Usual fixes:** tests that assert results and edge cases instead of only calling the code.

## `context.instructions_verified`: agent instructions are accurate

- **Reads:** AGENTS.md and CLAUDE.md at any depth, `.cursor/rules`, `.github/copilot-instructions.md` and `.instructions.md` files, CONTRIBUTING.md, skills, and the root README, in that order. A README command that an earlier file already gives is checked once, there.
- **Static pre-pass:** each command and path is checked first, by file and line: an install or add command with the wrong package manager, a pnpm, yarn or bun script run in a repo that uses another manager (npm, which every Node install has, may run scripts anywhere), a script missing from `package.json`, a missing Make target, a file that `node`, `python` or `./` runs and a folder that `cd` or `--directory` names that don't exist, and a path that doesn't exist. Each piece of a chain (`&&`, `;`, `|`) is checked, following `cd`. A command runs in the package that owns its instruction file, or in the folder a section says to work in ("Navigate to the `ui` directory"). A path counts when it exists next to the file, at the root, in that package, or as a package-relative path under it (`server/index.ts` for `src/everything/server/index.ts`).
- **Not counted:** README usage for the package's users outside a section about developing the repo, unless it runs one of the repo's own scripts or Make targets; commands that install or run the repo's own package; commands and paths named as an example ("like `x`"), inside link text, or in a sentence that says not to run them; paths the docs say are gone or will come later; prose paths relative to the reader's folder (`../repo-123`) and build output (`dist/`); steps written for another repository; `npm link`; a program a build or download makes first (`./app serve`); commands for a toolchain the audit doesn't assess, such as `go test`; and runner commands (`npx`, `pnpm dlx`, `uvx`) for a package the repo doesn't depend on, which need the network. Each item names the rule that decided it, and part 5 prints the rule.
- **Replay:** every remaining command runs in the clean container, inside `--budget-total`: each gets what's left of it, up to 5 minutes, and none starts once it's spent. Install commands are checked statically, since the replay runs the frozen install. Long-running commands (dev servers, watchers) and risky ones (deploy, publish, delete, network piped into a shell) are listed and not run.
- **Skipped:** commands with a placeholder to fill in (`<component>`), commands that ask questions (`init`, `create`, `login`), commands that add or remove packages (`pnpm add`, `npm i <pkg>`), and every command in a vendored third-party skill are listed as skipped and never run. A skill is vendored when `skills-lock.json` lists it, a license ships with it, or its frontmatter names a `source`. An instruction file reached twice, through a symlink or as an identical skill copy, is checked once.
- **Passes:** no item fails and every replayable command replayed. From 2026-12-beta only a command in a file written for agents (AGENTS.md, CLAUDE.md, Cursor rules and skills, Copilot instructions) counts: a wrong README or CONTRIBUTING item, or a wrong path anywhere, is listed in the report and doesn't hold Level 2 (`severities.instructions`).
- **Needs:** ran on host or stronger.
- **Why:** agents follow these files literally, so a stale command costs more than a missing one. The conventions scanned are AGENTS.md (Codex's `/init` and its root-to-folder discovery), GitHub's `copilot-instructions.md` and path-specific `.instructions.md`, and Cursor's `.cursor/rules` plus AGENTS.md. No outcome study yet measures how much these files help.

## `safety.execution_boundary`: normal work needs no production access

- **Fails on:** committed secrets (reported by type and line, never the value) outside tests, fixtures, docs, examples and generated code (from 2026-12-beta only a provider-shaped token, a private key with a body, and a literal password in a URL for a host on a real domain, `safety.blockingSecretClasses`), tests that read production credentials (an environment variable with `PROD`, `PRODUCTION` or `LIVE` as a word of its name and a secret word such as `KEY`, `TOKEN`, `PASSWORD`, `DSN` or `URL`, so `STRIPE_LIVE_KEY` counts and `PRODUCT_DATABASE_URL` doesn't; or a test failure that names a missing key, secret, token or password), and install hooks that pipe a download into a shell.
- **Lists for review without failing:** from 2026-12-beta, a long value assigned to a name that sounds secret (`API_KEY = '...'`), shown by its name and length, since public client keys an app ships, test values and placeholders look the same; a value a vendor documents as an example (AWS's documentation access key), a private key header with no key after it (a comment or a placeholder), a production credential read in a test fixture or written inside a string, a secret-shaped value in a test, fixture, eval, doc, example or generated file (such as `tests/`, `__tests__/`, `integration-tests/`, `test-utils/`, `*.test.js`, `*.spec.ts`, `docs/`, a Markdown file, `.env.example` or `__generated__/`), which is almost always a dummy, other install hooks, destructive scripts, deploy or publish scripts, and any setup or script that runs `sudo`.
- **Needs:** read from files.
- **Why:** agents run with whatever access setup gives them, so normal work must never need production credentials, and setup must not need more privilege than a container gives it. When a hook pipes a download into a shell, the replay installs with `--ignore-scripts` instead of running it. A command that uses `sudo` runs only inside the throwaway container, never on the host.

## Other signals (informational)

Part 5 lists six signals read from files. None of them sets a level or appears in part 1, and only the last can add a roadmap step.

- **CI config:** a GitHub Actions, GitLab CI, CircleCI or Buildkite config, and whether it runs tests.
- **A way to run one test file:** whether each assessed component's test runner takes a file or a name filter (`node --test`, vitest, jest, mocha, pytest), so an agent can rerun only the tests near its change.
- **Sample env file:** when the code reads environment variables of its own, whether a `.env.example` or similar names them.
- **Worktree and port isolation:** fixed ports and machine-specific absolute paths in package scripts, the environment setup, Makefiles, shell scripts and compose files, which collide when two agents work in separate worktrees.
- **AGENTS.md length:** the root AGENTS.md's word count, marked long over 900 words, since agents load all of it on every task.
- **A scripted way to drive the app (from 2026-12-beta):** whether an agent can start each assessed app and use it as a user would, not only run its tests. It counts Playwright, Cypress or WebdriverIO configs, a dependency on Playwright, Cypress, WebdriverIO, Puppeteer or a terminal harness (`node-pty`, `pexpect`), an `e2e` or `smoke` script, a smoke script under `scripts/`, and a `verify-<app>` skill with a Drive section or a feature map. A component counts as an app when it has a `start`, `dev`, `serve` or `preview` script, a start command, or a web framework dependency (Next.js, Vite, Express, Fastify, FastAPI, Flask, Django and similar). A harness inside a component counts for it, and one outside every component counts for all of them. The audit's own drafted skill (`.cursor/skills/verify/`) only runs commands, so it doesn't count. It reads n/a when no component is an app. When a component at Level 2 is an app with nothing to drive it, the roadmap adds a later step, "Give agents a way to drive" it, after "Give agents work in" it. That step changes no level, never appears in part 1, and closes once the signal finds a harness. The audit doesn't launch or drive the app itself.

An environment setup whose install or start uses `sudo` is listed in the agent assets as not a working setup, and `draft-skill` never puts a sudo command into agent setup.

## Met, not met, blocked and unknown

Every condition ends in one of four states. Met and not met come from a run at the strength the check needs. Blocked means a limit of this machine kept the deciding run from happening. Unknown means it didn't run for another reason, such as the time budget. A level needs every condition met.

No real results, no level: when no Level 1 check ran and passed, or failed for a reason in the repo, the report gives no level, plans no actions, adds no roadmap steps and says why. That covers an audit where no component could be assessed, where every check was blocked on this machine, and the read-only tier.

The report names each condition that holds the level where it is, and gives a confidence (high, medium or low) with its reasons. Confidence drops when setup ran on the host, a deciding check was blocked, part of the recent changes isn't assessed, or the scope was sampled. It's reported next to the level and never raises it.

## Why scripts own the results

The session that audits may later remediate. Factory's GDAL result reports 89.8% on a held-out suite with a separate validation system, against 35.8% for the same model working as a single agent. Caveat: one reported task ([repo](https://github.com/Factory-AI/pb-gdal-fable), [write-up](https://factory.ai/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)). So this skill keeps the grading out of the agent's hands: scripts create the evidence, plant the faults, compute the levels, seal the audit with a digest of the scripts and rubric, and flag weakened tests in `diff`.

## Not assessed by this rubric

Whether CI matches the local commands, flaky tests, the quality of error messages, how easily code can be found, outcome checks on held-out tasks, and (from 2026-12-beta) whether the lint command catches anything. The report names these as "not assessed", which is different from unknown.
